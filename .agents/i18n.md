# Internationalization

Use `next-i18next` for all application internationalization. Follow the App Router APIs supported by the installed `next-i18next` version; do not introduce another i18n library or runtime machine translation.

## Locales

- `bg` — Bulgarian; the source and default language.
- `en` — English.
- `tr` — Turkish.
- `uk` — Ukrainian.

## Baseline structure

Use this structure for the locale-aware App Router implementation:

```text
app/
  [locale]/
    layout.tsx
    page.tsx

i18n/
  locales/
    bg/
    en/
    tr/
    uk/

i18n.config.ts
proxy.ts
```

Keep locale-specific namespaces and translation resources under `i18n/locales/`. Use `i18n.config.ts` as the central locale configuration and `proxy.ts` for locale detection, routing behavior, and the Bulgarian clean-URL convention.

## Translation requirements

- Every user-visible string must come from a translation. Do not hardcode UI text in components, including navigation labels, buttons, forms, validation messages, empty states, accessibility labels, and error messages.
- Use semantic translation keys and keep the same key structure in all four locale files.
- Bulgarian is the source language. Whenever text is added or changed, update Bulgarian, English, Turkish, and Ukrainian together. Do not leave missing locale values or silently rely on fallback text.
- Keep translation data and locale configuration in the existing project structure. Keep the implementation simple and consistent with established conventions.

## Routing and links

- Use locale-aware routing throughout the App Router.
- Bulgarian should use clean URLs without a locale prefix where possible, for example `/services`.
- Other locales use a locale prefix, for example `/en/services`, `/tr/services`, and `/uk/services`.
- Internal links, redirects, navigation, breadcrumbs, forms, and language switchers must preserve the active locale.
- A language switcher should keep the user on the equivalent current page whenever an equivalent route exists. Fall back to the localized home page only when it does not.

## Metadata and SEO

- Translate page titles, descriptions, Open Graph and Twitter text, structured user-facing metadata, and other SEO copy in all supported locales.
- Set the document `html lang` value from the active locale.
- Generate correct locale-aware canonical URLs and `hreflang` alternates where applicable, including the Bulgarian default URL and prefixed URLs for other locales.
- Keep translated routes crawlable and maintain equivalent route mappings across locales where content exists.

## Implementation checks

When adding or changing a page or component, verify:

1. No user-visible text is hardcoded in the component or route.
2. The translation key exists with equivalent content in `bg`, `en`, `tr`, and `uk`.
3. Links and redirects retain the active locale and use the correct Bulgarian URL behavior.
4. Metadata, `html lang`, canonical URLs, and `hreflang` values are localized correctly.
5. Locale switching preserves the current page when possible.
